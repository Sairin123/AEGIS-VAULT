1. What is AES and why is AES-256-GCM selected over AES-CBC or AES-ECB?

Advanced Encryption Standard (AES), originally named Rijndael, is a symmetric block cipher standardized by NIST in 2001 (FIPS 197). It operates on 128-bit blocks using key sizes of 128, 192, or 256 bits.

Comparison of Modes:

  • ECB (Electronic Codebook): Insecure! Encrypts identical plaintext blocks into identical ciphertext blocks, preserving patterns (e.g., the famous ECB Tux penguin leak).
  • CBC (Cipher Block Chaining): Provides confidentiality but no integrity. Vulnerable to padding oracle attacks (e.g., POODLE) unless paired with Encrypt-then-MAC (HMAC-SHA256).
  • GCM (Galois/Counter Mode): The gold standard in modern network security (used in TLS 1.3). It is an AEAD (Authenticated Encryption with Associated Data) mode that provides both high-speed stream cipher encryption (Counter mode) and hardware-accelerated cryptographic integrity authentication using a 128-bit GHASH over Galois Field GF(2128).
2. Explain the 4 internal transformations executed in each round of AES.
  1. SubBytes (Non-linearity / Confusion): Each byte in the 4×4 state matrix is substituted using an 8-bit S-Box. The S-Box is constructed by finding the multiplicative inverse in Galois Field GF(28) with irreducible polynomial m(x) = x8 + x4 + x3 + x + 1 (0x11B), followed by an affine transformation to prevent fixed points.
  2. ShiftRows (Permutation / Diffusion): Rows of the state matrix are cyclically shifted to the left: Row 0 shifted by 0, Row 1 by 1, Row 2 by 2, and Row 3 by 3 bytes. This ensures bytes in each column spread across multiple columns.
  3. MixColumns (Diffusion): Each 4-byte column is multiplied by a fixed polynomial matrix over GF(28) with maximum branch number 5. This provides the avalanche effect (a 1-bit change affects all 4 bytes of the column). Note: MixColumns is omitted in the final round (Round 14) to maintain decryption symmetry.
  4. AddRoundKey: The 128-bit state matrix is combined with the 128-bit round subkey via bitwise XOR (⊕). The subkeys are generated from the master 256-bit key via the Key Expansion algorithm using RotWord, SubWord, and round constants Rcon.
3. What is a Zero-Knowledge Architecture in Password Managers?

In a Zero-Knowledge password manager, the service provider (server or storage backend) has zero mathematical knowledge of the user's master password, derived encryption keys, or plaintext vault data.

All cryptographic operations (Key Derivation via PBKDF2, AES-GCM encryption, and decryption) execute strictly client-side inside the user's volatile RAM. The master password is never transmitted across the network. If an attacker breaches the storage database, they only obtain strongly encrypted ciphertext blobs that are mathematically impossible to decrypt without the master password.

4. Why is PBKDF2 with 600,000 iterations used instead of simple SHA-256 or MD5?

Standard cryptographic hash functions like SHA-256 and MD5 are designed to be extremely fast for data integrity checks. A modern consumer GPU can compute over 3 billion SHA-256 hashes per second, allowing attackers to crack 8-character passwords in minutes.

PBKDF2 (Password-Based Key Derivation Function 2) implements Key Stretching by iterating HMAC-SHA256 hundreds of thousands of times (OWASP recommends 600,000 rounds for SHA-256). This imposes a steep computational and memory tax on brute-force attempts. A GPU that could test 3 billion passwords per second is throttled down to only a few thousand, rendering offline dictionary attacks economically and computationally infeasible.

5. What is the role of Nonce/IV and why must it NEVER be reused in AES-GCM?

An Initialization Vector (IV) or Nonce ensures that encrypting identical plaintext multiple times produces completely distinct ciphertexts, thwarting replay attacks and traffic pattern analysis.

In AES-GCM, reusing an IV with the same key is a cryptographic catastrophe known as the "Forbidden Attack". Because GCM uses Counter (CTR) mode internally, identical IVs generate identical keystreams: C1 ⊕ C2 = P1 ⊕ P2. Furthermore, an attacker can solve polynomial equations over the Galois Field GF(2128) to recover the GHASH authentication subkey H, completely destroying both confidentiality and integrity authentication!

6. How does k-Anonymity protect user privacy during breach checks?

Traditionally, checking if a password is compromised required sending the password or its hash to a remote server, which introduces a severe privacy risk. The k-Anonymity model solves this mathematically:

  1. The client hashes the password using SHA-1 (e.g., 5BAA61E4C9B93F3F0682250B6CF8331B7EE68FD8).
  2. The client takes ONLY the first 5 characters (prefix 5BAA6) and queries the breach database.
  3. The server returns a list of hundreds of hash suffixes matching that 5-char prefix.
  4. The client performs the match locally in its own memory.

The remote server never sees the remaining 35 characters of the hash or the plaintext password, ensuring mathematical zero-knowledge privacy.
